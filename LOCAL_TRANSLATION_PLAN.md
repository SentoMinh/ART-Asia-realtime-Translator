# Local translation model plan

Saved 2026-10-22 at the user's request. Scope: text translation after speech recognition, running on the user's PC. Speech-recognition and text-to-speech model variants are separate tasks.

## Decision rule

**Low latency first; other models remain alternatives.** Choose the lowest measured delay among models that preserve meaning, retain every sentence, use the requested language and avoid repeated or explanatory output. Keep the existing translator available while comparing candidates. A smaller model or faster token rate does not automatically produce a usable complete translation sooner.

Translation must work offline after setup. Download accessibility from China is a requirement for installation. The user prefers in-app online downloads: Hugging Face first, HF-Mirror on failure, with pinned revisions and hashes. Keep the existing offline package as an optional fallback. No mainland-China connection has been tested. Download size is not runtime RAM/VRAM usage.

## Settings and integration to evaluate

- For Qwen3, disable thinking in the actual chat template/runtime (`enable_thinking=False` where supported). Removing reasoning text after generation does not save its generation time. Qwen3.5 does not officially support Qwen3's textual thinking switches; verify its non-thinking template instead. See the linked Qwen model cards.
- Use text-only, translation-only prompts and validate model-specific decoding settings. Do not copy one model's temperature or repetition settings into every other model without testing.
- Keep the selected model loaded between utterances and measure startup separately. Current background `prepare()` loads installed weights without dummy generation; any proposed inference warm-up needs separate measurement. Use a short context and a bounded output allowance that still fits the complete translation. Reject truncated output instead of presenting it as successful.
- A localhost inference server is still fully local and can be evaluated through ART's Custom domain path. That path needs prompt/template, model-list and error-handling checks; it is not a claim that these candidates already work correctly in ART. The desired integrated experience remains Download → Use model in Local Model setup.
- The 27 October source defaults NLLB/Qwen to automatic device selection: CUDA requires one verified device, cuBLAS and memory checks for the model plus a 3 GiB game reserve; otherwise it uses CPU. `VRCT_LOCAL_DEVICE=cpu` forces CPU. Checks run immediately after loading and periodically before inference/while idle. Load/reserve failures use CPU in the current request; a CUDA inference error fails that line and uses CPU on the next request. Hy-MT2 remains CPU-only. A GPU speedup in isolation may disappear under shared load; live VRChat/headset and game-FPS checks remain outstanding.
- Select one active translator. Do not run every candidate or a second quality pass for every utterance; extra work and fallback delays count against latency.

## Measurements needed before choosing a default

1. Replay the same short conversational texts through each candidate: ordinary sentences, two-sentence messages, names, numbers, negation, VRChat terms, mixed languages, and stuttered recognition. Include the earlier repetition and missing-VR-sentence failures. Use material approved for testing.
2. Cover all six app languages, with particular attention to English/Chinese/Vietnamese and Cantonese. Have language-competent reviewers check meaning, sentence completeness and target language; do not infer quality solely from language-count claims.
3. Record cold startup separately from warm translation. For warm requests, measure median and p95 time from recognized text being ready to the first usable displayed translation and to the complete translation. Also count errors, omissions, repetition, retries and wrong-language results. First-token latency alone is insufficient.
4. Repeat the comparison with VRChat and live recognition sharing the PC. Record CPU, RAM, VRAM and impact on the game. Check one output language and three output languages separately; measure full speech-to-subtitle delay as well as translation-only time.
5. Record the exact model revision, file hash, quantization, runtime version, prompt, generation settings, thread counts and GPU offload. Set the acceptable latency/quality thresholds from the baseline and user experience before choosing a winner. No target milliseconds or performance results are invented here.

## Current status

- Hy-MT2 1.8B Q4_K_M (Tencent, Apache-2.0, GGUF revision `a0c709d9`, SHA-256 `dc5f44fc…6699`) is an optional CPU translator through llama.cpp 0.3.36, greedy decoding and Tencent's own prompt. On 31 local lines it kept meaning better than NLLB and Qwen2.5 3B Q4, at a median 914 ms versus NLLB's 330 ms and about twice the CPU. NLLB stays the default. Qwen2.5 3B was slower and left Chinese untranslated, so it is not offered. Evidence: `.tools/model-candidates/`.
- Qwen3 1.7B INT8 uses the bundled CTranslate2 Generator and tokenizers; no torch, transformers or inference server is needed. It uses a short translation-only prompt with cached target instructions, the official non-thinking assistant prefix, greedy decoding, one CPU thread by default (`VRCT_CPU_THREADS=2` restores two), a 1,024-token input limit and 512 output tokens. The 27 October pass may use CUDA when the 3 GiB reserve is available. It rejects missing EOS, runaway repetition, empty/reasoning output and obvious wrong-script output. These checks do not prove semantic accuracy.
- NLLB remains the default and its sentence/repetition handling is preserved. Switching models releases the previous weights; one shared lock serializes local translation across typed text and speech queues. No provider choices are changed during validation.
- The 27 October gaming pass measured summed warm translation time for one pass over three synthetic lines, excluding loading and a warm-up: NLLB GPU 0.21 s, CPU one thread 1.74 s, CPU two threads 1.06 s; Hy-MT2 one thread 4.55 s, two threads 2.50 s. Real NLLB/Qwen lifecycle checks matched one English-to-Vietnamese CPU/CUDA answer per model and fell back to CPU under injected low-memory telemetry; those lifecycle timings include loading. Runtime CUDA/OOM failures are covered by fake-runtime tests. These are component checks, not end-to-end latency or game FPS. Load, warm wall/CPU timings and limitations are separated in [LATENCY_REPORT.md](LATENCY_REPORT.md).
- Both new downloads passed full SHA-256 checks and real CPU inference. Qwen translated the short EN/ZH/VI examples and basic EN→JA/KO/YUE samples, but wording and Cantonese naturalness still need human review. The selected 1.7B model is an alternative, not a latency improvement. See LATENCY_REPORT.md.
- PhoWhisper Small is also integrated for Vietnamese hearing, with CPU INT8 and one thread by default (`VRCT_CPU_THREADS=2` for two). Two existing Vietnamese recordings matched their reference words (case aside) in forced-Vietnamese and Auto modes. Forced decoding took about 2.1–2.4 seconds and Auto 3.6–4.2 seconds in this small replay. Other accents, mixed-language speech and live microphone conditions are unverified.
- Mainland-China connectivity, fresh-machine installation, broad translation quality and controlled game-contention testing remain outstanding.
- Speaker identification remains deferred as recorded in [ROADMAP.md](ROADMAP.md).
